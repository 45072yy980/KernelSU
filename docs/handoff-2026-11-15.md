## 二、月虹的 GhostKey 是什么

`/sdcard/MT2/apks/月虹提权助手_v1.6.8.apk` 里有两套东西：

| 目录 | 内容 |
|---|---|
| `assets/ghostlock/` | 43499（GhostLock）的 kernel profile，与本项目已有的 ghostlock 链同源 |
| `assets/ghostkey/` | 98260（GhostKey）的 kernel profile + 一份 `ksud` |

GhostKey 的载荷是 `lib/arm64-v8a/libcve98260.so`（PIE，不是普通共享库），
接口：

```
calibrate-a    KASLR slide 探针（写 $CVE98260_HOME/slide.txt）
calibrate-b    page_offset 校准（写 $CVE98260_HOME/page_offset.txt）
exploit        UAF 注入 + cred 接管（--slide --page-offset --daemon-exit）
ksu-takeover   rootd 以 uid=0 接管 KernelSU
su <cmd>       临时 root 的 su 客户端
rootd-stop     停掉持有 cred 页的 rootd
dump-config    打印当前加载的内核表
```

Java 侧的编排（`com.GhostKey.app.shizuku.Cve98260UserService`）是：

1. `calibrate-a` 读 `slide.txt`，拿不到就中止（**这一步只读，不写内核**）；
2. `calibrate-b --slide` 读 `page_offset.txt`，拿不到就用 profile 默认值；
3. `exploit --slide --page-offset --daemon-exit`，主进程退出、子进程持页跑 rootd；
4. 用 `su -c id` 复检，出现 `uid=0` 才算成功；
5. 可选 `ksu-takeover`，再拉起 ksud 守护进程。

## 三、profile / blob 格式（已逐字节验证）

Java 侧 `writeBlob` 会先写 **4 字节大端长度**（=308），再写 308 字节主体，
所以递给载荷的是 **312 字节**。主体布局：

| 偏移（主体内） | 长度 | 含义 |
|---|---|---|
| 0 | 4 | `"C982"` |
| 4 | 2 | `u16le` version = 4 |
| 6 | 2 | `u16le` recommend_shizuku |
| 8 | 64 | 8 × `u64le`：page_offset / timer_link / cred_link / selinux_link / user_ns / root_user / groups / ucounts |
| 72 | 16 | 4 × `u32le`：task_cred / task_struct_size / cred_uid / kitimer_node |
| 88 | 128 | release（C 字符串，最多 127 字节） |
| 216 | 32 | vuln_type（最多 31 字节，通常是 `cve-2026-98260`） |
| 248 | 8 | `u64le` kitimer_size |
| 256 | 8 | `u64le` task_alloc_link |
| 264 | 44 | 11 × `u32le`：cred_size / cap_inh / cap_perm / cap_eff / cap_bset / cap_amb / security / user / user_ns / ucounts / groups |

旧项目里的 `C982Blob.kt` 与这个布局是同一份（旧版 version=3，把 recommend 位当 0）；
月虹只是把 version 提到 4，并显式带 recommend_shizuku。

## 五、为什么旧 98260 会被判成“没有 ez 表”

`EzProfile.keyOf()` 取的是 `g([0-9a-f]{4,})` 的前 **6** 位，
f72a 这颗内核会得到 `f72a02`，而资源文件名是 `ez98260-f72a.json`。
`ExploitAssets.ezProfile()` 只按这个 key 找，找不到就返回 null，
上层便得到“没有 ez 表或 fast 成品”的结论，随后整条链在 `3a44a06e` 被删。

所以**不是内核没有表，是查找 key 截断错了**。恢复 98260 时优先修这里，
不要重新生成一份表。

## 六、硬约束：GhostKey 的校准需要 shell / Shizuku

应用进程在这台机器上是 `u:r:untrusted_app_27:s0`，
`/sys/kernel/tracing`、`/proc/kallsyms`、`/proc/modules` 全部 `Permission denied`。
实测 `calibrate-a`：

```

[calib_a] error: cannot arm kmem_cache_alloc (tracefs not writable?)
```

月虹自己也是走 Shizuku UserService（`uid=2000, Seccomp=0`）跑的。

因此接入 GhostKey 有两条路：

1. **Shizuku 路线（与月虹一致）**：用 `Shizuku.newProcess` 起 `calibrate-a/b` 与

   但现有代码只用于 root 启动内置 server，没有 `newProcess`。
2. **免 Shizuku 路线**：必须先拿到 KASLR slide，再跳过 `calibrate-a`。
   这正是 98432 的 leak 阶段可以提供的值；在 98432 没打通之前，做不到。

## 七、98432 现在缺什么

已确认的部分：

- 结构偏移与 `k1.elf` BTF 一致：`task_struct=0x12c0`、`cred=0x820`、
  `real_cred=0x818`、`cred.uid=0x8`、`cap_*=0x30..0x50`、`security=0x80`。
- 漏洞未修：`6.6.118-f72a` 上 `kfree` 仍是裸释放、`optlen` 仍读两次。
- `probe` 通道、`race` 三态判定（40 / 0 / 其他）已有骨架。

明确的缺口 / 可疑点：

1. **LEAK 被当成成功**：`AutoEscalation` 与 `FlashUtils` 在 `Phase.LEAK` 返回 ok 时
   直接报成功；此时并没有 root。应先判 `rootAvailable()`，或在 ROOT 段成功前
   只报“泄露阶段通过”。
2. **竞态源地址与设计相反**：README 要求源地址不属于任何直连子网，以拉长
   `inet_csk_route_req()` 的 FIB/邻居解析窗口；代码里 `SPOOF_SOURCE=10.7.7.99`
   正好在 tun 的 10.7.7.0/24 里，窗口会被缩短。
3. **leak 时序不对**：命中后才 `complete()` + 喷射，但被读的 SYNACK 已经收完；
   应该“先喷射占位、再让重传路径回读”，并把回读的 optlen/字节解析出来，
   不能只判 `opts[3] == 0x53`。
4. **ROOT 段没有实现**：写原语（`ip_build_and_send_pkt` 二次读 optlen 造成越界写）
   还只是 README 里的方案，代码中没有对应函数；Kotlin 侧直接返回“不启用”。

## 十、GhostKey 管理器修正（2026-11-15 晚）

真机跑出来的问题：GhostKey 成功给了 root，但管的不是 DikSU，而是官方 KernelSU。
原因是我们把月虹包里那份 **官方 ksud** 当成了 `CVE98260_KSUD`，`ksu-takeover`
自然装的是官方的那套（内核 ko 也是官方的签名/包名）。

修正：

- `GhostKeyRunner` 不再从 assets 取 ksud，改用本应用 nativeLibraryDir 里的
  `libksud.so`（内嵌 DikSU 自己的各 KMI `kernelsu.ko`，默认包名也是 DikSU）。
- 删掉 `assets/exploit/ghostkey/ksud`（6.4MB，官方那份），APK 也小一圈。
- 接管前先读 `Natives.isManager`；如果内核里已经有 kernelsu 但不是 DikSU：
  标记 `foreignKsu`，提示“请重启后重跑”，自动提权不计成功，进度页给重启按钮。
- 接管脚本的 `live()` 在 `/proc/modules` 已有 kernelsu 时会直接 `already_live`
  退出，所以**不能**在同一会话里换管理器；必须重启得到干净的内核态。


## 十一、SynOpt（原 98432）改名与竞态修正（2026-11-15）

弹窗里的四条链现在统一成 CamelCase：

| 名称 | 漏洞 | 来源 |
|---|---|---|
| GhostLock | CVE-2026-43499 | 自有 |
| DirtyFrag | CVE-2026-43284 | 自有 |
| GhostKey | CVE-2026-98260 | 移植自月虹 |
| **SynOpt** | CVE-2026-98432 | 自有 |

SynOpt = **SYN** + IP **Opt**ions，取自漏洞入口：入站 SYN 携带 IPv4 选项，
`ireq_opt` 在握手完成时被裸 `kfree`，而 SYNACK 路径还在 RCU 里读它。

代码同步改名：`c98432/` → `synopt/`、`C98432Runner` → `SynOptRunner`、
`C98432VpnService` → `SynOptVpnService`、`libc98432.so` → `libsynopt.so`、
`FlashIt.IReqOpt98432` → `FlashIt.SynOpt`、`METHOD_C98432` → `METHOD_SYNOPT`
（值从 `cve98432` 改成 `synopt`，老用户存的自定义顺序会回落到默认）。

### 竞态为什么原来跑不通

对着 `k1.elf` 反汇编确认了三件事：

1. `inet_sock_destruct` 里的 `kfree` 是**裸释放**（`bl kfree`，不是 `kfree_rcu`），
   `tcp_v4_reqsk_destructor` 同样是 `ldr x0,[x0,#256]; bl kfree` —— 漏洞没修。
2. `tcp_v4_syn_recv_sock` 在 `inet_ehash_nolisten` 成功之后才
   `str xzr,[x21,#256]` 清空 `req->ireq_opt`；失败路径（子 socket 被丢弃）
   **不清空**，请求 sock 还挂着原指针 —— 这是更宽的窗口。
3. `tcp_v4_send_synack` 在 `__rcu_read_lock()` 里
   `ldr x4,[x20,#256]` 取 `ireq_opt`，然后一路带到 `ip_build_and_send_pkt`
   → `ip_options_build` 的 `memcpy`。中间没有任何引用计数。

原来的实现有三个硬伤：

- 喷淋是**命中之后**才做的，那时 SYNACK 已经收完，回读无从谈起；
- 竞态对撞只发 SYN+ACK，**不发 RST**，子 socket 不会销毁，`kfree` 永远不发生；
- 判定只看 `opts[3]==0x53`，分不清“被自己对象复用”和“读到残留堆”。

### 现在的做法

- 喷淋改成后台线程持续“关一批→重新分配一批”，竞态全程在 `kmalloc-96`
  里进出；命中即停，避免对象被下一轮改掉。
- 对撞改成 SYN / ACK / RST 三连：ACK 让 `ireq_opt` 移交给子 socket 并置空，
  RST 紧跟其后让子 socket 走 `inet_sock_destruct` 触发 `kfree`。
- 命中后**不再发包**（发 RST 可能让已经指向喷射对象的 `inet_opt` 二次释放，
  在 `PANIC_ON_OOPS=y` 上直接重启），直接解析已经收到的 SYNACK：
  `dump_opts` 打字节，`is_spray_tag` 判断是否被自己对象占据，
  `find_text_candidates` 挑 `0xffff` 开头、页对齐的 `.text` 指针候选。

### 仍然缺的

写原语（`root` 阶段）没有实现，Kotlin 侧仍直接拒绝。SynOpt 现在能做的
是：通道验证 → 竞态命中 → 回读并挑内核指针候选。要把候选换成 KASLR 基址，
还需要一张本机构建的 `.text` 站点表（`ip_options_build` 里的
`opt->__data` 偏移、`cred_link` 之类），目前只有 ghostlock 那套里有。


## 十二、SynOpt 站点表与写原语（2026-11-15 下午）

### 站点表从哪来

只需要 `/root/workspace/rmx/k1.elf`（42MB，本机这颗内核的带符号镜像）：

- `.symtab`（110,326 个符号）→ 所有函数/全局变量的绝对地址；
- 内嵌 BTF（`__start_BTF`..`__stop_BTF`）→ 所有结构体字段偏移。

`O_*` = 绝对地址 − `_text`（`0xffffffc080000000`）。已写进
`manager/app/src/main/cpp/synopt/synopt_offsets.h`：

```
ip_options_build 0xe9ff9c   kfree 0x317a7c      init_task 0x213e2c0
ip_build_and_send_pkt 0xea154c  __kmalloc 0x31773c  init_cred 0x2150788
tcp_v4_send_synack 0xed0c78  commit_creds 0xe45e8  selinux_state 0x237a350
tcp_v4_syn_recv_sock 0xed0f04  prepare_kernel_cred 0xe4af4
inet_csk_route_req 0xeae984   modprobe_path 0x21cc888
inet_sock_destruct 0xef1968   core_pattern 0x2201ae0
tcp_v4_reqsk_destructor 0xed0af0
tcp_make_synack 0xeca440
```

### 写原语的关键：add_key 补上了最后一块

`ip_options_rcu` 的 `optlen` 在 `+0x18`，而 IP 选项最多 40 字节、
`kzalloc` 时后续是 0 —— 光靠 `setsockopt(IP_OPTIONS)` 改不到这个字段。

`add_key("user", ...)` 正好补上：`user_preparse` 里是
`__kmalloc(datalen + 0x18)`，`user_key_payload` 布局为
`rcu_head(0x00) + datalen(0x10) + data(0x18)`，与 `ip_options_rcu` 的
`rcu_head(0x00) + ip_options(0x10)` **完全重合**：

| ip_options_rcu | user_key_payload | 含义 |
|---|---|---|
| +0x10 | +0x10 | ip_options / datalen |
| +0x18 | +0x18 | **optlen** / data[0] |
| +0x20 | +0x20 | __data / data[8..] |

`datalen=72` → 分配 96 字节 → kmalloc-96，和 `sizeof(ip_options_rcu)+40=88`
同一个缓存。于是 `data[0]=56` 就是假 optlen，`data[8..]` 就是假 `__data`。

第一次读 optlen=40 预留 60 字节头，第二次读到 56，`memcpy` 写穿 16 字节。

### root 阶段现在能做什么

1. 从泄露候选解 `_text` 基址（候选 × 站点偏移 × 2MiB 对齐自洽性）；
2. 打印关键符号的运行时地址；
3. 验证 `add_key` 通路（喷 256 个 96 字节 key 再释放）。

真的写内核必须显式 `--allow-write`（Kotlin 侧 `allowWrite=false` 默认拒绝）。
越界长度控制在 16 字节、不跨页。

### 还没做的

- 越界写的**落点**还没选：目前只是证明原语可达，没有把 16 字节定向到
  cred 或 `skb_shared_info`。要定向需要先把泄露候选换算成具体对象地址。
- 泄露阶段能不能稳定拿到内核指针，还没有实机数据。

## 十三、SynOpt 暂停（2026-11-28）

这条链**主动停在竞态参数搜索之前**，不再占用开发轮次。结论和遗留工作：

### 已验证的事实（真机日志 2026-11-28 14:14）

- 通道全通：ICMP 回、带 40 字节选项的 SYN 能拿到 SYNACK（对照 5/5）、
  闭端口回 RST、accept 队列能取到连接。
- 漏洞对象确实在 `kmalloc-64`（`optlen + 12 = 52`），喷淋也改到了同一个桶。
- **重传前提成立**：`[rtx]` 探针 1.5 秒内收到 2 个 SYNACK，
  说明 `reqsk_timer_handler → tcp_rtx_synack` 这条定时器路径是活的。

### 卡在哪

20 批 ACK 扫描里绝大多数批次「一个 TCP 包都没有」，只有 2 批零星收到
1 个和 4 个。也就是重传发生了，但补 ACK 的扫描窗口没盖住它 —— 要么
起点偏早（ACK 把 req 提前摘走、定时器被取消），要么覆盖太窄。

这是纯参数搜索，不是代码缺陷。所以最后一轮把时序参数改成运行时开关
（提交 `58687859`），同一份 APK 就能扫参数空间：

```
--batch    每批并行几个四元组（默认 20，上限 RACE_BATCH=20）
--wait-ms  SYN 之后等多久开始补 ACK（默认 950，夹到 0~5000）
--sweep-ms ACK 扫描持续多久（默认 300，夹到 1~2000）
--burst    每毫秒打几轮（默认 8，夹到 1~64）
--spray-n  喷淋 socket 数（默认 192，上限 512）
```

启动时统一夹区间并打印 `[cfg]`，日志里那行就是真正生效的值。

### 继续做的时候从哪下手

1. 先只调 `--wait-ms`：从 950 起按 25ms 步进扫到 1200，`--sweep-ms 400`
   覆盖整个不确定范围，看哪个起点开始能稳定收到重传包。
2. 窗口对上之后再看 `clear` 细分：`注入 ACK 后变空` 非零说明竞态撞上了，
   但指针已经被置空（ACK 太早）；`hit` 非零才是喷淋对象占住了槽位。
3. 写原语仍然是硬关闭的（`--allow-write` 解析成 0），不参与自动提权，
   Kotlin 侧 `isAvailable(METHOD_SYNOPT)` 返回 `false`。恢复写入前必须先
   把 16 字节越界定向到 cred，现在只是证明原语可达。

## 十四、两条第三方 GhostKey 实现的逆向（2026-11-28）

用户提供 `Shark_2.6.26.apk` 与 `TimerRoot_8.7.apk`，问能不能借它们的思路提速。
结论：**两条都是 CVE-2026-98260**，但实现路线和我们不同；真正能借的是它们的
**运行形态**，不是算法。

### 共同点：都不往 /data/local/tmp 部署任何东西

Shark 手册原文：

> 所有入口都直接以 App 原生库（`nativeLibraryDir`）原地运行，子进程
> cwd/HOME/TMPDIR 都在 App filesDir，**不向 `/data/local/tmp` 部署工具或写文件**；
> ksud 也从已安装的管理器 APK 原地执行。

Shark 自述快速路径 plant 2~3 秒、全流程 4~9 秒。我们原来的流程每次要经
Shizuku 的 stdin 写 69KB 载荷 + 312B profile，KSU 接管前还要写 **6.9MB** 的
ksud（APK 里未压缩存储），再外加每阶段一次取日志的往返。这些固定开销加起来
比 exploit 本身还大，是速度差距的主要来源。

### Shark（libk66118.so，488KB，PIE）

- 一个进程内跑完 preflight → 98260 UAF → ksud late-load → 收尾，不再分阶段
  重启进程。
- 校准用 **POSIX timer**（`timer_create`/`timer_settime`）+ ftrace 的
  `kmem_cache_alloc` / `mm_page_alloc` / `rss_stat` 事件交叉定位；
  日志键 `[calib] timers=%d`、`[base] made=%d timers=%d pages=%d best=%#llx`。
- 竞态失败有**重试与回收**机制，不是一次定生死：
  `PYB110_CHASE` / `PYB110_CHASE_MS` / `PYB110_REPAIR`，
  日志 `[chase] plant%d no free in %dms; chasing`、
  `[repair] plant%d miss repaired; retryable`、
  `[repair] page pfn=%#llx ...; reaping`。
- 按**精确 uname -r** 选 `libk<版本>.so`，每个内核一个独立载荷。
- 失败后 plant 持有的页会转交 holder，**同一 boot 可直接再点一次**，不必重启。

### TimerRoot（t98260_plant / prep_solve / forker）

- 校准是**抓包后离线求解**：8 个 `per_cpu/cpuN/trace_pipe_raw` 并行落盘，
  再用 `prep_solve` 从 `sched_blocked_reason` 事件反推 slide。
  `take_slide.sh` 里注释写明「4 线程跑，比 2 线程快一倍」。
- 有**样本量下限**：`run98260.sh` 里 `OBS < 800` 直接判 `ABORT 样本太少`，
  宁可失败也不接受不可靠的 slide。这个判据值得学。
- 符号表按 `uname -r` 分发（`assets/timeroot/syms-<release>.txt`），
  和我们的 profile 思路一致。
- `BUDGET=%llds` 有整体预算，`RETRY=timers` / `RETRY=leak-timers n=%d`
  按阶段重试。

### 已经落地的改动

见提交 `12424b56`：载荷移到 `jniLibs/arm64-v8a/` 原地执行、ksud 直接用
nativeLibraryDir 路径、落地合并成一次往返、阶段日志与阶段本身合并、
rootd 轮询 1s→100ms、su 复检前三次 0.1s 退避。

### 还没借的（按性价比排序）

1. **单进程跑完整个流程**：我们现在仍是「一个阶段一个进程」。参考实现都是
   一个进程内做完，省掉每次重新装载载荷、重新建 tun 之外的一切。
   改动大，需要载荷支持串行子命令。
2. **样本量下限**：`[calib_a] warn: weak support samples` 现在只是警告，
   可以照 TimerRoot 的做法直接判失败，避免用不可靠的 slide 去写内核。
3. **失败后同 boot 重试**：我们失败就要求重启；Shark 把页转交 holder 后
   可以直接再跑一次。需要载荷侧支持，收益是用户少一次重启。

### susfs4ksu-for-lkm 适配（同轮）

`inforcqb/susfs4ksu-for-lkm` 是 SUSFS 的 LKM 版。适配结论：

- 它的 reboot 超级调用与我们 ksud **完全同源**（`KSU_INSTALL_MAGIC1=0xDEADBEEF`、
  `SUSFS_MAGIC=0xFAFAFAFA`、命令 ID 逐个一致、结构体逐字段一致），
  所以现有客户端直接可用，不需要另写一套。
- 唯一命名差异：`CMD_SUSFS_HIDE_SUS_MNTS_FOR_NON_SU_PROCS`（LKM）vs
  我们的 `CMD_SUSFS_HIDE_SUS_MOUNTS_FOR_NON_SU_PROCS`，**数值都是 0x55561**，
  只是拼写不同，无功能影响。
- 补上它独有的 `CMD_SUSFS_SET_PRIORITY_UID_FILTER`（0x60030）与
  `st_susfs_priority_uid_filter`（`app_strings[65535] + err`）。内建实现回 126，
  `send()` 把 126 当「不支持」正常返回。
- 补上它独有的 `/proc/susfs_map`、`/proc/susfs_opath` 两个节点。
- **坑**：LKM 的 `/proc` 节点受模块参数 `expose_proc` 控制（`susfs_main_data.c`
  里默认 true，但模块的 `load.sh` 显式传 `expose_proc=1`）。关掉时节点全不存在，
  管理器读到的快照是空的，看起来像功能坏了。界面现在按 `variant == "GKI-LKM"`
  识别并直接给出原因与修法。
