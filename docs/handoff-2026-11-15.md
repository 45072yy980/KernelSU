# 交接 · 2026-11-15：月虹 GhostKey 与 CVE-2026-98432

> 上一份交接是 `docs/handoff-2026-11-07.md`。本文只覆盖提权链这一块：
> 月虹提权助手 v1.6.8 的 GhostKey 链路逆向结果、f72a 的 profile 已经验证到哪一步，
> 以及自有 98432 链现在缺什么。**没有改动任何内核代码，也没有在真机上跑 exploit。**

## 一、当前基线

- 设备内核：`6.6.118-android15-8-gf72a02f47f4b-abogki551678766-4k`
- 本机镜像：`/root/workspace/rmx/k1.elf`（同名 release，带 BTF 与符号表）
- HEAD：`3a44a06e`（已删掉 98260/64560，98432 顶到弹窗第三项）
- 当前 98432 只实现 `probe / race / leak` 三段；`root` 段在 Kotlin 侧直接拒绝。

## 二、月虹的 GhostKey 是什么

`/sdcard/MT2/apks/月虹提权助手_v1.6.8.apk` 里有两套东西：

| 目录 | 内容 |
|---|---|
| `assets/ghostlock/` | 43499（GhostLock）的 kernel profile，与本项目已有的 ghostlock 链同源 |
| `assets/ghostkey/` | 98260（GhostKey）的 kernel profile + 一份 `ksud` |

GhostKey 的载荷是 `lib/arm64-v8a/libcve98260.so`（PIE，不是普通共享库），
接口：

```
calibrate-a    KASLR slide 探针（写 $CVE98260_HOME/slide.txt）
calibrate-b    page_offset 校准（写 $CVE98260_HOME/page_offset.txt）
exploit        UAF 注入 + cred 接管（--slide --page-offset --daemon-exit）
ksu-takeover   rootd 以 uid=0 接管 KernelSU
su <cmd>       临时 root 的 su 客户端
rootd-stop     停掉持有 cred 页的 rootd
dump-config    打印当前加载的内核表
```

Java 侧的编排（`com.GhostKey.app.shizuku.Cve98260UserService`）是：

1. `calibrate-a` 读 `slide.txt`，拿不到就中止（**这一步只读，不写内核**）；
2. `calibrate-b --slide` 读 `page_offset.txt`，拿不到就用 profile 默认值；
3. `exploit --slide --page-offset --daemon-exit`，主进程退出、子进程持页跑 rootd；
4. 用 `su -c id` 复检，出现 `uid=0` 才算成功；
5. 可选 `ksu-takeover`，再拉起 ksud 守护进程。

## 三、profile / blob 格式（已逐字节验证）

Java 侧 `writeBlob` 会先写 **4 字节大端长度**（=308），再写 308 字节主体，
所以递给载荷的是 **312 字节**。主体布局：

| 偏移（主体内） | 长度 | 含义 |
|---|---|---|
| 0 | 4 | `"C982"` |
| 4 | 2 | `u16le` version = 4 |
| 6 | 2 | `u16le` recommend_shizuku |
| 8 | 64 | 8 × `u64le`：page_offset / timer_link / cred_link / selinux_link / user_ns / root_user / groups / ucounts |
| 72 | 16 | 4 × `u32le`：task_cred / task_struct_size / cred_uid / kitimer_node |
| 88 | 128 | release（C 字符串，最多 127 字节） |
| 216 | 32 | vuln_type（最多 31 字节，通常是 `cve-2026-98260`） |
| 248 | 8 | `u64le` kitimer_size |
| 256 | 8 | `u64le` task_alloc_link |
| 264 | 44 | 11 × `u32le`：cred_size / cap_inh / cap_perm / cap_eff / cap_bset / cap_amb / security / user / user_ns / ucounts / groups |

旧项目里的 `C982Blob.kt` 与这个布局是同一份（旧版 version=3，把 recommend 位当 0）；
月虹只是把 version 提到 4，并显式带 recommend_shizuku。

## 五、为什么旧 98260 会被判成“没有 ez 表”

`EzProfile.keyOf()` 取的是 `g([0-9a-f]{4,})` 的前 **6** 位，
f72a 这颗内核会得到 `f72a02`，而资源文件名是 `ez98260-f72a.json`。
`ExploitAssets.ezProfile()` 只按这个 key 找，找不到就返回 null，
上层便得到“没有 ez 表或 fast 成品”的结论，随后整条链在 `3a44a06e` 被删。

所以**不是内核没有表，是查找 key 截断错了**。恢复 98260 时优先修这里，
不要重新生成一份表。

## 六、硬约束：GhostKey 的校准需要 shell / Shizuku

应用进程在这台机器上是 `u:r:untrusted_app_27:s0`，
`/sys/kernel/tracing`、`/proc/kallsyms`、`/proc/modules` 全部 `Permission denied`。
实测 `calibrate-a`：

```
[calib_a] collecting call sites (timer_link=0xffffffc080195d9c, probe 2048 / hold 2s)
[calib_a] error: cannot arm kmem_cache_alloc (tracefs not writable?)
C98260_STATUS calib_a failed
```

月虹自己也是走 Shizuku UserService（`uid=2000, Seccomp=0`）跑的。
本机已安装 Shizuku（`moe.shizuku.privileged.api`）。

因此接入 GhostKey 有两条路：

1. **Shizuku 路线（与月虹一致）**：用 `Shizuku.newProcess` 起 `calibrate-a/b` 与
   `exploit`。需要新增权限请求与一条 shell 通道；DikSU 已有 Shizuku 客户端代码，
   但现有代码只用于 root 启动内置 server，没有 `newProcess`。
2. **免 Shizuku 路线**：必须先拿到 KASLR slide，再跳过 `calibrate-a`。
   这正是 98432 的 leak 阶段可以提供的值；在 98432 没打通之前，做不到。

## 七、98432 现在缺什么

已确认的部分：

- 结构偏移与 `k1.elf` BTF 一致：`task_struct=0x12c0`、`cred=0x820`、
  `real_cred=0x818`、`cred.uid=0x8`、`cap_*=0x30..0x50`、`security=0x80`。
- 漏洞未修：`6.6.118-f72a` 上 `kfree` 仍是裸释放、`optlen` 仍读两次。
- `probe` 通道、`race` 三态判定（40 / 0 / 其他）已有骨架。

明确的缺口 / 可疑点：

1. **LEAK 被当成成功**：`AutoEscalation` 与 `FlashUtils` 在 `Phase.LEAK` 返回 ok 时
   直接报成功；此时并没有 root。应先判 `rootAvailable()`，或在 ROOT 段成功前
   只报“泄露阶段通过”。
2. **竞态源地址与设计相反**：README 要求源地址不属于任何直连子网，以拉长
   `inet_csk_route_req()` 的 FIB/邻居解析窗口；代码里 `SPOOF_SOURCE=10.7.7.99`
   正好在 tun 的 10.7.7.0/24 里，窗口会被缩短。
3. **leak 时序不对**：命中后才 `complete()` + 喷射，但被读的 SYNACK 已经收完；
   应该“先喷射占位、再让重传路径回读”，并把回读的 optlen/字节解析出来，
   不能只判 `opts[3] == 0x53`。
4. **ROOT 段没有实现**：写原语（`ip_build_and_send_pkt` 二次读 optlen 造成越界写）
   还只是 README 里的方案，代码中没有对应函数；Kotlin 侧直接返回“不启用”。

## 八、建议的下一步

按风险从低到高：

1. 修 `EzProfile.keyOf`，先让旧 98260 的 ez 查找恢复（不改 UI，只修查找）。
2. 把 GhostKey runner 接进来（用月虹的 `libcve98260.so` + 本文件第四节的 profile），
   先接 Shizuku；跑通 `calibrate-a → calibrate-b → exploit → su -c id`。
3. 98432 先把 LEAK 判定和竞态时序修正，再谈写原语；写原语没有真机验证前
   不要把它设成自动提权的成功路径。

给 98432 起名的候选（用户还没定）：`IReqOpt` / `TunRace` / `SynOpt`。
代码里现有 `C98432Runner`、`FlashIt.IReqOpt98432`，改名要连 UI 文案一起动。
