## 一、先把话说明白：这里的"臃肿"有两类

这个仓库是 fork，树里混着**三种来源**的代码。整治时**必须分类对待**，
否则会把上游的东西改乱，将来合不回去。

| 来源 | 举例 | 能不能动 |
|---|---|---|
| **上游 KernelSU** | `kernel/supercall/dispatch.c`、`kernel/selinux/sepolicy.c`、`userspace/ksud/src/boot_patch.rs` | ❌ **原则上不动**。上游还在发版，改了以后每次合并都要手动解冲突 |
| **作者版 DikSU** | `userspace/ksud/src/webui*.rs`、`lkm_image.rs`、`module.rs`、`MiuixStock` 那套 UI | ⚠️ **谨慎**。属于基线，动了等于和作者分叉 |
| **本分支新增** | 越狱模式（`magica/`、`AppZygotePreload`、`ksud_integration.c`）、`kernel/feature/partition_guard.c`、管理器 UI 改动、版本号逻辑 | ✅ **优先整治**。这是我们的债，想怎么改都行 |

**结论**：整治的主战场是**第三类**。前两类只在**确实挡路**（比如 bug 就在里面）时才碰，
并且改动要小、要能说清楚为什么。

## 三、可疑点（按优先级，尚未验证）

下列都**只是"看着可疑"，没有确认**。动手前每一项都要先读代码、给出证据。

### P0 — 我们自己写的，且已经踩过坑

- **`kernel/feature/partition_guard.c`**
  钩子挂在 `write` 这类热路径上，每写一次都要 `fget_raw` + `S_ISBLK`。
  要确认：判断能否提前到 fd 层做一次；`clang-format off` 包住的表是否有更规整的写法。

- **管理器里"移植期"留下的代码**
  早期改动大量依赖一次性脚本（`patch_*.py`）打进去，**同一个功能可能有好几处
  互相覆盖的补丁痕迹**。要找出：重复的判断、被后来覆盖但没删的旧分支、
  注释里还写着的旧行为。
  线索：`HomeMiuix.kt` / `HomeScreen.kt` / `MainActivity.kt` 里关于
  `bottomInnerPadding`、毛玻璃、提示卡片的逻辑。

- **版本号逻辑**
  `manager/build.gradle.kts` 与 `kernel/Kbuild` 现在各写一份公式。
  两处必须永远一致，但没有任何机制保证。要评估：能否收敛到一处
  （例如让构建时把解析结果传给内核侧），或者至少加一个校验。

## 四、动手时的规矩

1. **先只读体检，出证据**：`grep` / 读代码 / 统计，不靠印象下结论。
2. **一次只动一件事**，每件事单独一个提交，**附 diff 说明**。
3. **不碰上游代码**，除非能证明 bug 就在那里。
4. **改完不构建**——构建要等我明确说"构建"。
   （见 `docs/` 里关于发布流程的说明：tag 驱动、`fetch-depth: 0`、Release opt-in。）
5. **有疑问先问**，不要猜。这个项目已经因为"瞎猜乱改"吃过亏。
